# ESP32-only 版本進度紀錄：從加密示範到具備認證與復原能力的 UART 影像串流

紀錄日期：2026 年 9 月 11 日  
比較基準：上一個 Git commit `847021d8`（`esp32 only`）與本次尚未提交的工作目錄。  
本次定位：開始 WiFi 開發前的 UART 安全影像串流基準版本。

## 一、這次開發為什麼從測試與穩定性開始

上一版已經能讓 ESP32 與電腦完成 ML-KEM-768 金鑰交換、AES-256-GCM 影像加解密、定期換鑰，以及 ML-DSA-44 簽章驗證。這代表主要密碼元件可以共同運作，但還不能直接等同於具備完整身分認證、異常處理與長時間運作能力的通訊系統。

開發期間曾出現程式執行一段時間後退出的情況。當時 traceback 顯示，Host 在讀取影像的 GCM tag 長度標頭時，只收到預期 4 bytes 中的 3 bytes，接著因逾時而退出。這個現象常被稱為「閃退」，但能確認的是 Python 程式因未完成的接收操作拋出例外；不能僅憑這個訊息判定 ESP32 本身當機。

因此，這次的重點不是單純增加密碼函式，而是回答幾個實際問題：電腦如何知道對方是可信任的 ESP32？合法的舊影像是否可能被重複接受？封包收不完整時能否恢復？裝置是否曾重新開機？測試成功又能證明到什麼程度？

## 二、將 DSA 從功能驗證擴充為裝置身分認證

上一版能驗證裝置產生的簽章，並測試修改被簽署訊息後驗證會失敗。但如果驗證所用的公鑰也是從同一條尚未可信任的連線取得，Host 只能證明「簽章與這把公鑰相符」，無法據此確認對方就是原本那台裝置。

本次將 ESP32 的 ML-DSA 身分公私鑰保存於 NVS。正常重新啟動時重用同一份身分，避免每次開機產生不同公鑰。Host 則透過可信任的實體連線與人工核對 SHA-256 指紋，登錄裝置公鑰並保存為 `host/trusted_device.pub`。這個檔案是公鑰信任資料，不是私鑰；將它排除於 Git，是為了避免把某台本機裝置的信任設定當成所有使用者的預設。

建立 session 時，Host 產生新的隨機挑戰，ESP32 對挑戰與 KEM 公鑰組成的訊息簽章。Host 必須使用已登錄公鑰驗證成功，才繼續金鑰交換。之後再透過綁定挑戰、KEM 公鑰、KEM 密文及 epoch 的 HMAC，確認裝置確實持有本次 session 金鑰。這些步驟也用於目前的每次 rekey。

這項修改的目的，是讓影像接收建立在已確認的裝置身分與新鮮握手之上，而不是只證明某個加密函式可以運算。原本可對 Host 訊息簽章的 `DSA_SIGN` 命令，也加入認證保留前綴的拒絕規則，避免它被拿來產生可冒充認證回應的簽章。

同時新增獨立的 `dsa-validation` 驗證工具及裝置認證測試，涵蓋訊息／簽章修改、截斷、錯誤公鑰、舊證明配新挑戰、KEM 公鑰替換及用途前綴等情境。測試的目的，是區分「正常資料會通過」與「不應接受的資料確實被拒絕」。

目前仍是單向認證：電腦認證 ESP32，ESP32 尚未驗證連線電腦的身分。NVS 持久保存身分也不等於防止實體讀取私鑰，本版尚未加入 Flash Encryption 或 Secure Boot。

## 三、把偶發退出轉成可追查的接收紀錄

只有 terminal 最後一段錯誤，往往無法還原問題發生前的狀態。本次新增 JSONL 診斷，將每個事件逐筆寫入並 flush，使正常測試與異常退出都能留下分析依據。

接收紀錄包含 metadata、nonce、ciphertext、tag 各階段的宣告長度、實收長度與耗時，並附上請求編號、最後驗證成功的 frame_id 及預期 epoch。讀取失敗時記錄發生在哪個標頭或資料區段，避免只剩下籠統的「接收逾時」。正常加密交易不記錄 payload、私鑰或共享秘密。

韌體端則加入 binary writeFrame 的短寫補送與 TX 計數。如果 Serial.write 回傳的已寫長度小於要求長度，就繼續補送剩餘資料；無進度達到限制時記錄失敗。這是對可能短寫的防護，並不代表已證明先前問題就是短寫造成。TX 成功也只表示驅動接受資料，不保證電腦一定收到全部 bytes。

此外，Host 補強例外時的連線與視窗收尾。整合相機 Host 後來依測試需求移除影片寫檔，保留接收、解密、驗證、顯示與診斷功能，避免反覆測試產生大量 AVI。

## 四、區分封包短讀與輪次之間的裝置重啟

多輪測試期間曾發現 frame_id 在新一輪歸零。原本只看正常結束訊息，無法判斷這是計數重設，還是 ESP32 實際重啟。

本次新增每次開機的隨機 boot_id、reset reason、uptime，以及每輪開始／結束的 CAMERA_INFO 和 TX_INFO 快照。boot_id 僅用於診斷，不是 DSA 裝置身分，也不作為安全認證依據。Host 開埠後原本會清掉的啟動資料，也改為有限量保存。

加入紀錄後，一批 10 輪測試顯示：9 次輪次交接中有 7 次 boot_id 改變，且新一輪 uptime 約 2.9 秒；每輪錄影期間 boot_id 則保持不變。這表示問題集中在兩輪交接附近，而不是單憑「錄影成功」就能宣稱裝置從未重啟。

檢查 Host 發現，原本先開啟 COM，再把 DTR／RTS 設為 False。修改後先建立未開埠的 Serial 物件、設定控制線並停用硬體流量控制，最後才 open。後續從 `trace_20260910_230632` 開始的 10 輪測試，全程使用相同 boot_id，9,219 幀從 1566 到 10784 連續，沒有輪次間重啟。

這支持開埠順序修改對本次硬體環境有效，但必須保留兩個結論的差異：輪次間重啟已有改善證據；最初 tag header 只收到 3／4 bytes 的根因仍未確定。後來沒有再發生同樣的偶發退出，不足以反推唯一原因。

## 五、補上影像序號與 session 防重播檢查

AES-GCM 可以檢查資料是否被修改，但一份曾經合法的密文仍可能再次通過同一把金鑰的驗證。因此，只有驗證 tag 並不足以阻止相同 session 內的影像重播。

本次新增每條連線獨立的接收狀態，保存目前 epoch、最後接受的 frame_id 與 session 幀數。Host 在 GCM 驗證成功、JPEG 頭尾檢查通過後，才檢查並更新序號。後續 frame_id 必須等於上一幀加一，重複、倒序、跳號與計數回繞都會被拒絕。

正常 rekey 時，epoch 必須遞增，session 幀數重新計算，但影像 frame_id 必須接續。新連線第一幀則允許任意合法序號，因為裝置可能已運行一段時間；跨連線的舊資料由重新認證及新 session 金鑰隔離，不能把 epoch 本身當成全域唯一的 session 身分。

文字回應中的 count 與 rekey flag 也加入一致性檢查，但這些文字尚未受 GCM 保護，不能把它們視為密碼認證證據。

相關測試使用真正的 AES-GCM 封包走正式接收函式，驗證合法連續幀、重播、倒序、舊 epoch、相同 epoch 但不同 session 金鑰，以及 metadata／tag 篡改不會污染接收狀態。

## 六、封包不完整時，先重新同步再恢復影像

原本相機接收逾時會直接結束。若只是捕捉例外後繼續讀，殘餘密文可能被誤當成下一個封包標頭，讓通訊狀態更混亂。因此本次復原的核心，是先確立新的訊息邊界，再重新認證與建立金鑰。

Host 在 record 模式的相機接收逾時後，放棄不完整影像與舊 session 的使用，送出帶有本次隨機 token 的 RECOVER 命令。韌體只會在上一筆命令返回後處理它，清除 session、重新產生 KEM keypair，再回覆獨立的同步標記。Host 有限量排空舊資料，找到本次標記後才重新設定串流、驗證裝置及確認新 session 金鑰。

同步標記本身不是身分證明，不能取代 DSA 驗證。被放棄的影像也不算成功幀；新 session 重新建立接收序號基準，之後恢復嚴格連號，所以不能把「復原成功」描述為全程沒有丟幀。

每輪預設最多復原兩次，可以透過參數關閉或調整。額度耗盡、同步失敗、重新認證失敗會停止並保留錯誤。GCM、簽章、防重播驗證失敗不會一律自動重試，避免掩蓋安全異常。USB 拔除、其他命令逾時及完整斷線重連仍不在本次自動復原範圍。

為了不必等待偶發故障，新增一次性故障注入：在指定相機請求的 tag header 收到 3 bytes 後刻意停止，留下剩餘資料，測試排空及重新握手。實機測試成功復原一次，之後繼續接收並完成 DSA 驗證。這驗證了不完整接收的復原路徑，但不等同於已重現所有物理 UART 丟資料情況。

## 八、專案整理與提交範圍

本次保留原本的獨立相機及密碼測試，新增 DSA 驗證工具、認證／防重播／復原測試，以及各功能說明文件。UART 相關設定有調整至 921600 baud，部分獨立相機測試也有設定變動。

依測試需求刪除舊錄影，包含四個上一版已受 Git 追蹤的 AVI。根目錄 gitignore 補上診斷資料、暫存歸檔、Python 快取、隔離測試依賴與本機信任公鑰等規則；同時取消過度廣泛的 txt 忽略規則，讓需要保留的文字文件可以被追蹤。

整合相機 Host 的 record 模式現在不儲存影片，即使舊指令保留 output 參數也會忽略；照片模式與獨立 camera-tests 錄影工具仍保留原用途。工作目錄另外存在環境 requirements 與操作筆記，提交時應區分它們與核心功能修改。

## 九、目前版本的目的與下一步

這次將上一版的加密示範，推進為具備持久装置身分、可信公鑰登錄、新鮮握手、防重播、接收診斷與有限復原能力的 UART 影像串流版本。重點不只是「加解密可以成功」，而是明確定義接受資料的條件、失敗後如何處理，以及如何用紀錄驗證行為。

原始短讀的根因仍保持未定論；目前可以確認的是，輪次間重啟已有改善證據，而且不完整接收不再只有直接退出一種處理方式。

下一階段優先完成 WiFi 功能：先讓單台 ESP32 與電腦連接同一個手機熱點，透過 TCP 傳送既有加密影像，再處理無線斷線及兩台裝置同時連線。現階段尚未實作 WiFi 或多裝置支援。

rekey 間隔繼續保留為可調參數，不以拉長間隔來宣稱效能改善。背景準備金鑰、降低換鑰停頓，以及竊聽／金鑰外洩實驗，待基本功能完成後再進行。現有共享秘密直接用於 AES 與 HMAC 的用途分離、未認證控制命令，以及完整通訊安全模型，也仍需後續設計，不能將本版宣稱為完整或形式化驗證過的安全協定。
